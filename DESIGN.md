# Design

The repository has two deployable parts.

```text
Codex plugin                          User-owned Cloudflare account
  prompt/capture hooks  ───────────▶  Worker API
  MCP search/getDocument ◀─────────   D1 + Vectorize + Workers AI
```

`client/` stores completed task records with deterministic v2 capture keys and custom IDs in the shared `memories` container. The server assigns a UUID on first insertion and retains it when the same custom ID is retried. Repository identity is stored separately as project provenance and does not partition new storage. The persisted `metadata.sm_project_id` field is retained as a 1.x compatibility contract alongside `metadata.project`; it is not a current product name. Existing records keep their server IDs and physical containers, and capture reuses a matching live legacy record instead of moving it. Forgotten legacy records are not reuse targets; retrying a forgotten shared record restores that canonical row. Manual saves also default to `memories`, with an explicit `containerTag` overriding storage. Manual forget accepts a document ID or exact stored content and is restricted to that explicit or default container; an ID must match a live record in the named container.

Recall ranks concise metadata indexes by the user's current topic without restricting results to the current folder. The client requests `POST /v4/search` with `allContainers: true`, and the server searches all live containers with one query embedding and one namespace-unrestricted Vectorize lookup. Explicit `containerTag` and `sm_scope` searches retain their filters and revision checks. Lexical search remains available when AI or Vectorize fails; D1 semantic fallback remains bounded to 200 rows. An older server that explicitly rejects global search, or returns the legacy response shape, uses the former discovery and per-container path. That compatibility path is capped at 100 discovered spaces and reports a full page as incomplete; authentication, server, and network errors do not trigger fan-out retries.

Automatic recall requests `indexOnly` results. The server combines bounded lexical, semantic, and direct index/topic candidates before applying the final limit, so Vectorize's top 50 and reciprocal-rank overlap cannot remove a matching index. It reads source content in chunks of at most 50 rows from at most 200 candidates, derives compatible indexes for legacy documents without updating stored metadata, and returns compact provenance and index metadata. SQL index matching uses Unicode case variants to retain non-ASCII uppercase labels. Missing query terms found in a source body can appear in a bounded 240-character original excerpt, labeled as an original passage rather than a new fact. Semantic scores alone still do not inject unrelated indexes automatically; manual search retains semantic-only candidates and full search excerpts, including matching original passages. Legacy servers still hydrate documents without indexes. `getDocument` remains the path to the complete source before reuse. Topic browsing uses its separate cross-container list API.

Project consolidation runs server-side rather than in lifecycle hooks. Records with a nonempty `metadata.sm_project_id` are grouped across containers by that provenance ID; records without one are grouped by physical container. Checkpoints are always stored in `memories`. The Worker keeps the existing 15-minute vector reconciliation schedule and uses a distinct daily cron at 18:00 UTC (03:00 JST) to inspect those groups. A new project becomes due when it has at least 20 unconsolidated records or three days have elapsed since its oldest pending record. After a successful checkpoint, the three-day interval is measured from that success. An initial backfill that has started but remains incomplete stays due so it can resume without meeting those thresholds again.

The first due scheduled run for a project drains its complete historical backlog through successive batches of at most 40 new records, carrying the prior checkpoint forward between batches. Recurring scheduled work handles one batch for each of at most 25 due projects per invocation. The authenticated `POST /v4/consolidate` endpoint and the MCP `consolidate_memory` tool use the same service. The endpoint applies normal due thresholds unless `force` is true; the MCP tool always sends `force: true`. Each manual request still processes at most one batch and requires at least one unconsolidated source record.

Migration `0005_memory_consolidations.sql` records consolidation state and exact source membership separately from user metadata. A published checkpoint is a new memory row; its persisted metadata contains a bounded source-ID preview. Global index-only recall returns the exact membership intersection with the returned candidates, keeping ranking metadata bounded independently of project history. Explicit-container compatibility searches still return complete membership. Source rows are never deleted by consolidation. Publishing a replacement marks the former checkpoint superseded. Source upsert, update, forget, or hard delete invalidates dependent checkpoints so stale or forgotten content cannot remain visible through them. Automatic recall ranks topic relevance first and favors an active checkpoint at equal relevance. Only a checkpoint in the final selection suppresses an original, and only when it covers that original's matching query terms; a specific detail omitted from a checkpoint can still expose its original. Manual search retains originals. Generation failures and failed source-revision publication guards do not publish a replacement or consume pending sources. A previous checkpoint remains active only while its own sources remain valid.

Workers AI receives the previous checkpoint plus bounded excerpts from the next source batch as untrusted data. Its structured output separates verified, unverified, unresolved, and next-action claims; exact membership preserves provenance but does not imply that every source detail survives summarization. Generated checkpoints skip fact extraction to avoid turning synthesized claims into project facts.

Consolidation generation requests bounded output within the existing token budget. A truncated or invalid JSON response is retried once with the same source input and a more compact output schema. Two invalid responses publish nothing and leave sources pending; diagnostics record the finish reason and output length without logging the generated text. Re-enrichment atomically changes a source revision and invalidates its dependent checkpoints, while re-enriching a checkpoint preserves its disabled fact extraction. Consolidation also checks existing checkpoint membership after acquiring the project lease and invalidates stale checkpoints before rebuilding from live sources, so installations with old revision mismatches can recover through their normal scheduled or manual path.

Unexpected enrichment failures log the document revision and mark only pending or processing stages failed when D1 is available, preserving completed stages. These updates retain the same revision and forgotten-record guards as enrichment publication. A second failure while recording the status is logged separately, and the original background rejection remains visible to Workers. Retrying a legacy checkpoint also removes any facts previously derived from that checkpoint and restores supported source facts in the same guarded transaction.

Capture retains JSON sent-document receipts and coordinates their updates through Node's built-in SQLite under `kagayoi-memory/capture-state/` in the selected Codex home. It unions receipts from the former `cloudflare-memory/capture-state/` location and writes future updates to the current location, preventing an upgrade from resending acknowledged turns. Deterministic capture keys and retrying unacknowledged records preserve retry safety; configured secrets are redacted before capture. Current records keep session and part bookkeeping in metadata instead of the user-facing body. Retrieval removes only the exact generated header from legacy v2 bodies, preserving unmatched user Markdown and existing split boundaries. Codex's official local memory store remains outside this integration.

`server/` owns authentication, persistence, lexical and semantic search, enrichment, and document retrieval. Each installation uses resources in the user's Cloudflare account. Client configuration contains only that installation's HTTPS endpoint and API key.

Migration `0004_content_topics.sql` adds revisioned `memory_topics` rows and classification state. Workers AI extracts content topics alongside facts; explicit validated `metadata.topics` can supply labels. Topic labels describe content, while containers remain physical storage and project metadata remains provenance. Fact support and supersession lookup is restricted to matching project provenance within a container, so shared storage does not make one project's facts replace another's.

`GET /v4/topics` lists topic counts and an unclassified count. `POST /v3/documents/list` spans all containers by default, with optional container and normalized exact-topic filters; `__unclassified__` selects records without current topic rows. Its optional `projection` selects the compatible full response or the compact `index`, `ids`, and `capture` shapes used by bundled callers. The topic setup batch also sets `enrichmentEligible` so opt-out records do not block older classification targets. Topic reads join against the document's current revision and omit forgotten records. Updates and enrichment retries replace the revision; guarded D1 batches prevent stale work from publishing topics or facts. Updating or forgetting a record removes its derived fact/topic rows and reactivates facts that no remaining live record supersedes.

Vectorize entries carry the document revision, while D1 remains authoritative for search and reconciliation. Vector status and reconciliation split lookups into batches of at most 20 IDs. Forgetting a record or superseding a checkpoint marks its vector for deletion; the 15-minute reconciliation rechecks forgotten rows and retries removal even when AI enrichment is disabled. A late upsert that loses its D1 revision guard is cleaned up, and a concurrent delete of a restored active record re-registers its current vector. Failed or still-visible deletions remain eligible for later reconciliation.

Enrichment is asynchronous and independently tracks embedding, vector, fact, and topic outcomes. Records with `metadata.memoryIndex.recallable` set to `false` remain stored and manually searchable, but are excluded from automatic recall and automatic embedding, fact, topic, and vector enrichment; explicit topics are still stored. Disabled, failed, or deliberately skipped classification leaves records available through unclassified browsing. `scripts/setup-topics.mjs` previews a bounded enrichment-eligible batch from that view; `--apply` submits those IDs to `POST /v4/enrich` using the existing backend, without adding a queue service. Acceptance is not completion, and re-enrichment refreshes other derived data too. This keeps classification within existing Workers AI usage at the cost of requiring callers to observe completion before selecting another batch. Server migrations precede clients that depend on topic APIs.

`scripts/setup-server.mjs` handles resource discovery, resumable provisioning, migrations, deployment, and endpoint verification. Its default mode is read-only; `--apply` enables changes. For default names that were not explicitly selected, discovery can fall back to existing 1.x `cloudflare-supermemory` D1, Vectorize, and Worker resources when the current-name counterpart is absent, instead of creating an empty replacement. Generated resource identifiers remain in the ignored local Wrangler configuration. The distributable package includes the example configuration and migrations, but excludes local state and credentials.

Codex loads an installed plugin copy from its cache. Kagayoi Memory uses the `kagayoi-memory` plugin ID and `dist/kagayoi-memory` distribution directory, keeps connection settings in `~/.codex/kagayoi-memory.json`, and keeps capture receipts under the Codex home directory so reinstalling the plugin does not discard them. The 1.x compatibility reader can import the former `supermemory.json` connection file without changing stored document IDs or legacy spaces. Hook trust is managed by Codex and requires review of each current definition. A new task picks up updated skills and MCP tools.

The package uses Codex's `.codex-plugin/plugin.json` format because Codex 0.153.4 does not load lifecycle hooks from portable Agent Plugin manifests. Its legacy MCP configuration sets `cwd` to `.`; Codex resolves that directory against the installed plugin root. The launcher path is relative to that root, while workspace provenance comes from MCP roots or an explicit `sourceFolder`, never the server process directory.

Repository entry points are `.codex-plugin/`, `.mcp.json`, and `hooks/` for plugin wiring; `client/` for MCP, recall, and capture; `server/` for the Worker and migrations; `scripts/` for launchers, setup, and packaging; and `skills/setup-kagayoi-memory/` for the setup workflow. Development checks are maintained in [AGENTS.md](AGENTS.md); installation and operation are in [README.md](README.md).
